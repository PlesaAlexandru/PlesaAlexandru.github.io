## Objective

After participating in one too many incident response activities, PicoSecure has decided to conduct a threat simulation and detection engineering engagement to bolster its malware detection capabilities. You have been assigned to work with an external penetration tester in an iterative purple-team scenario. The tester will be attempting to execute malware samples on a simulated internal user workstation. At the same time, you will need to configure PicoSecure's security tools to detect and prevent the malware from executing.  

Following the **Pyramid of Pain's** ascending priority of indicators, your objective is to increase the simulated adversaries' cost of operations and chase them away for good. Each level of the pyramid allows you to detect and prevent various indicators of attack.

### First step: Third party Verification / Internal Verification  

Having a closer look at the results, we can see that is a Trojan made in / executed in Metasploit, an  framework for finding vulnerabilities and exploiting them.  

**What is the file?**  
`sample1.exe` is an executable file, with the size of 202.5KB (important for later)
Before we look at any more details, let's put the hash in a VirusTotal scan.  
![](../../assets/Pasted%20image%2020261019010311.png)
**Detection Rate:** **62 / 71 security vendors** flagged the file as malicious, confirming high-confidence classification as a Metasploit-generated Trojan.  

**Anomaly Note: File Size Discrepancy**  
During cross-referencing, a discrepancy in file size was observed despite identical cryptographic hashes:  

| File provided in the simulation | File shown in the VirusTotal |
| ------------------------------- | ---------------------------- |
| `202.50 KB`                     | `7.00 KB`                    |

The difference could be explained either by the difference between Memory and Virtual Size or by the way that simulated sandbox is working. In any case, the hashes being the same means the file is the same.  

**Why is this file malicious?**  
It is shown multiple times as being a Trojan (is an app that should look legit but actually hides a malicious payload, similar to the trojan horse analogy). Also, the metasploit is also mentioned, which is a pentesting framework packed with exploits and payloads. Also, meterpreter is mentioned, which is a payload used for post-exploitation with an command-and-control interface.  

So, we know it is **malicious**, as seen in the bottom we got a couple of reasons on why based on behaviour.  

![](../../assets/Pasted%20image%2020261018185723.png)

### Second step: Blocking the malicious file  

Here we have limited options, but for this one we are going to block the sample with `Hash Blocking`
File blocking via hash, generally is not recommended because of how hashing works. Changing even 1 byte will totally change the entire hash, which is a common practice to bypass the same target. It is also on the lowest level on the Pyramid of Pain.  

**Steps:** 
1. Go to manage hashes  
2. Select the type of hash and paste it in the Hash Value  
3. Submit (if the hash is correctly blocked, it will turn green as in the picture below)  

![](../../assets/Pasted%20image%2020261018185831.png)

After we successfully blocked the hash, we receive the first flag along side with another email from the same sender. This time with another `.exe` file attached.

### Second step: Blocking the malicious file  

This time, as mentioned in the email, blocking it by hash will not be enough. The next option would be to block via IP.  

**Steps:**
1. Go to Firewall Rule Manager
2. Create a new rule with the following details
3. Save rule (If done correctly, It should turn green and You should have a popup notification with the flag / an email )

![](../../assets/Pasted%20image%2020261019140852.png)

Before we move on, I wanted to explain the rule in case anyone needs it.  
Type: Egress (Outgoing - The request is an GET request from our machine to another)  
Source IP: Any (We don't care what is our IP, if we have to block an Outgoing request we can block Any Source IPs)  
Destination IP: 154.35.10.113 (Is the malicious address)  
Action: Deny (To block the attack)

### Second step: Blocking the malicious file  

**Steps:**
1. Go to Sigma Rule Builder  
2. Select Sysmon Event Logs  
3. Select Registry Modification  
4. Add the key (Path towards the rule)  
5. Add Registry Name (The rule's name)  
6. Add Value 1 (1 = Enable, 0 = Disable)  
7. ATTCK ID (We didn't have the TA0112 available so the next option is TA0005 Defense Evasion)  
8. Validate Rule

### First step: Third party Verification / Internal Verification

As we can see, the host `10[.]10[.]15[.]12` is sending 97 bytes every 30 minutes, which is more of an heartbeat signal ("I am alive" message to the attacker). This C2 behaviour is constant through the whole log file.  
Let's use internal Malware Sandbox to check `sample5.exe` for more details.  
![](../../assets/Pasted%20image%2020261018192704.png)
![](../../assets/Pasted%20image%2020261018192710.png)
![](../../assets/Pasted%20image%2020261018192716.png)

HTTP Request shows 2 instances, one is `sample5.exe` and another `beacon.bat` (Self explanatory name). A GET method (to get the `beacon.bat`) and one is POST (For the keep-alive function). An important fact is that we can see the hostname (?hostname=WK102).  

DNS request is showing only one instance: `bababa10la[.]cn` and based on the information provided, it is a Cloud Service provider that could be a legitimate service. So blocking the whole DNS is not the way to go.  

Third Party Services didn't return anything worth mentioning.  

In anyway, we can block the network connections, via a similar way as the behaviour blocking.  

### Second step: Blocking the malicious file  

For the blocking method, we are going to use Network Blocking, but we want to block the keep alive signal, which have a constant 97 bytes every 30 minutes.  

![](../../assets/Pasted%20image%2020261018193855.png)

**Steps:**
1. Go to Sigma Rule Builder  
2. Select Sysmon Event Logs  
3. Select Network Connections  
4. Add the remote IP  (Any because the IPs can change)
5. Add the remote PORT (Any because the ports can change)  
6. Add Size (97 bytes because the keep alive signal is constant 97 bytes)
7. Add frequency
8. ATTCK ID (`Command and Control TA0011`)
9. Validate Rule

### First step: Third party Verification / Internal Verification

Here we can see a string full of commands with something in common, every command is collected to the `exfiltr8.log` file from `%temp%`.  So it is a post exploitation log file that collects data from the machine. (Exfiltration -  Exfiltr8 is also a name used just to make it obvious).

**List and short description of the commands:**

`dir c:\ >> %temp%\exfiltr8.log` - Lists root directory contents  

`dir "c:\Documents and Settings" >> %temp%\exfiltr8.log` - Lists legacy user profiles and folders  

`dir "c:\Program Files\" >> %temp%\exfiltr8.log `- Checks installed software and applications  

`dir d:\ >> %temp%\exfiltr8.log `- Lists secondary drive contents  

`net localgroup administrator >> %temp%\exfiltr8.log `- Identifies local admin users  

`ver >> %temp%\exfiltr8.log` - Gets the Windows OS build/version  

`systeminfo >> %temp%\exfiltr8.log `- Gathers detailed OS, hardware, and patch information  

`ipconfig /all >> %temp%\exfiltr8.log `- Dumps complete network adapter configuration  

`netstat -ano >> %temp%\exfiltr8.log` - Displays active network connections, ports, and PIDs  

`net start >> %temp%\exfiltr8.log `- Lists currently running Windows **services**  


### Second step: Blocking the malicious file  

**Steps:**
1. Go to Sigma Rule Builder  
2. Select Sysmon Event Logs  
3. Select File Creation and Modification (Storing means modification)  
4. Add the general file path %temp%
5. Add the file name `exfiltr8.log`  
6. Add ATTCK ID (Exfiltration TA0010)
7. Validate Rule

## Conclusions and Ending note

Overall, an enjoyable challenge with easy to understand simulated space. Not a true challenge to be fair but at least it puts in perspective the Pyramid of Pain which is really important to also have an hand on support for the theory.

We saw how one malware can go multiple stages to bypass the detections and restrictions. From file sizing, hashes, DNS, behaviours and other artifacts we discovered the file is malicious and reused in other attacks on the same target/host by modifying or adapting based on the rules.
